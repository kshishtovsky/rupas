# Перформанс-аудит Android-приложения Rupas

Дата: 2026-10-28 · Устройство: Samsung SM-S938B (Galaxy S25 Ultra), Android 16,
сборка `0.7.0` (versionCode 700), 8 ядер · Замеры через `adb` на живом
устройстве, код — по репозиторию на `v0.7.0`.

Вопрос, на который отвечает аудит: приложение обновляется/опрашивает что-то
чаще, чем нужно, из-за этого садится батарея и «network stability ниже».
Ниже — что реально происходит, с цифрами.

---

## 1. Сводка замеров

| Состояние | ΔCPU за окно | % одного ядра | Как измерено |
|---|---|---|---|
| Экран выключен, VPN **выключен**, приложение в фоне | 0.05 с / 120 с | **0.04 %** | `/proc/<pid>/stat` (utime+stime), 100 Гц |
| Экран выключен, VPN **включён**, трафика пользователя нет | 2.52 с / 120 с | **2.1 %** | то же |
| Экран включён, вкладка «Главная», VPN выключен | 1.19 с / 60 с | **2.0 %** | то же |
| Сутки целиком (с последней зарядки, реальный профиль) | u=22.7 с + s=27.4 с за 1 ч 09 м | **1.2 % в среднем** | `dumpsys batterystats --charged` |

Из batterystats: foreground service жил 58 из 69 минут, всего CPU ≈ 50 с/час →
**≈17 минут CPU в сутки**. Wake-lock'ов и `AlarmManager` у приложения **нет**
(`dumpsys alarm` и `jobscheduler` по uid пусты) — то есть мы не будим систему,
стоимость — это непрерывная работа VPN-сервиса.

Ключевой вывод по «постоянно опрашивает»: **на Android runaway-поллинга нет.**
В фоне вкладка «Главная» перестаёт опрашивать демона (проверено `onPause` →
`resumed=false`, `MainActivity:471`), и процесс в фоне стоит 0.04 % ядра.
Дорогая часть — не опрос, а **сам трафик через туннель**.

---

## 2. Находки, по убыванию стоимости

### P1. Каждый TCP-поток = отдельное TLS-соединение до VPS (мультиплексирования нет)

`internal/transport/android/relay.go` (`endpointOutbound`): у VLESS/hysteria2/
trojan нет `Multiplex` → sing-box поднимает новое соединение на **каждое**
входящее соединение приложения. Политика по умолчанию — `default: TUNNEL`
(48 правил, экран «Настройки → Маршрутизация»), то есть через туннель идёт
трафик **всех** приложений телефона, включая фоновые.

Что это значит в цифрах и в журнале (реальные строки с устройства):

```
19:12:13.171  tcp 172.217.113.4:443: CH sni="play.googleapis.com" ech=true
19:12:13.173  inbound/mixed[rupas-in-0]: inbound connection to 172.217.113.4:443
19:12:13.175  outbound/vless[rupas-out-0]: outbound connection to 172.217.113.4:443
19:11:53.627  tcp 78.29.1.40:443: dial refused: dial tcp 78.29.1.40:443: i/o timeout
```

Фоновые приложения открывают десятки соединений в минуту → десятки полных
TLS-handshake'ов до VPS в минуту: это и CPU (крипта, ~2 % ядра), и расход
радио, и каждая неудача (`i/o timeout`) видна пользователю как «сеть тупит».

Цена: основная часть тех самых 2.1 %/17 мин CPU в сутки.

**Что делать (по возрастанию цены вмешательства):**
1. Включить мультиплексирование в outbound (`Multiplex: {Enabled: true,
   Protocol: "h2mux", MaxStreams: 8}`) — один TLS-канал на 8 потоков вместо
   восьми handshake'ов. Требует поддержки на сервере (xray/sing-box mux).
2. Не гнать через туннель то, что не заблокировано: сейчас `default: TUNNEL`
   отправляет в VPS в том числе play.googleapis.com, appmetrica и прочий
   фоновый служебный трафик. `default: direct` с явными TUNNEL-зонами
   (TG-CIDR, Discord, голос) снимает почти весь фоновый поток с туннеля —
   это ровно та политика, что уже работает на десктопе по `docs/PRD.md`.
3. Только после 1–2 — микрооптимизации ниже.

### P2. Поллинг статуса 1 Гц на переднем плане: ~2 % ядра при выключенном VPN

`MainActivity:64` `TELEMETRY_POLL_INTERVAL_MS = 1000`, `MainActivity:159-165`:
каждую секунду `Core.status()` (JNI → Go), внутри — `eng.Snapshot()`,
`CarrierStates()`, `AdblockState()`, `TunnelInfo()`, затем `json.Marshal` и
`JSONObject` на стороне Java, потом `refreshUI()` с переустановкой текстов.

Замер: 1.19 с CPU на 60 с = ~20 мс на тик в UI-потоке. При выключенном VPN
полезной информации за тик почти нет (счётчики нулевые), но цена платится.

**Что делать:** 1 Гц → 2 с для счётчиков, а «сессия» и статус — по событиям;
либо отдавать из Go лёгкий статус (только rx/tx/flows/state) на каждый тик,
а тяжёлые `CarrierStates`/`AdblockState` — раз в 5 с. Экономия: ~1 % ядра на
экране, ~половина JNI-вызовов.

### P3. sing-box пишет INFO на каждое соединение, и это доходит до Java-журнала

`relay.go:377` ставит `Level: "warn"`, но в журнале на устройстве — строки
`sing-box info: INFO[0359] inbound/mixed...` / `outbound/vless...`. То есть
фильтр уровня до платформенного writer'а не применяется, и `WriteMessage`
(`relay.go:576`) пропускает всё, что не `Trace` (`level > LevelDebug`).

Каждая такая строка = Java-строка + запись в `LogBuffer` (1000 строк) + notify
подписчикам; при открытой вкладке «Журнал» — рендер до 4 раз в секунду
(`MainActivity:172`, `250 мс`). На устройстве в простое ~10 строк / 30 с, при
активности — в разы больше.

**Что делать:** фильтровать по уровню явно (`level != LevelError && level !=
LevelWarn && !verbose → drop`) и держать INFO только для режима «Подробный».
Экономия — аллокации/GC и строки в журнале, десятки процентов «шума» в
`LogBuffer`.

### P4. Flow-table GC тикает каждую секунду

`internal/capture/engine.go:41` `gcTick = time.Second` → 86 400 пробуждений
планировщика в сутки, даже когда таблица потоков пуста (VPN только что поднят).
Сама проба дешёвая (микросекунды), но это тот самый «постоянно что-то
проверяет», который видно в `top` как ровный фон.

**Что делать:** `gcTick` 1 с → 3–5 с. TTL потоков — десятки секунд, задержка
сборки на 2 с ничего не меняет; teardown-путь от этого не зависит.

### P5. Десктопный health-маркер: полный TLS-handshake каждые 30 с (Android не затронут)

`internal/tunnel/health.go` + `tunnel.go:137`: `GET https://www.gstatic.com/generate_204`
каждые 30 с, с `DisableKeepAlives: true` → **новое соединение и полный
handshake на каждую пробу**, 2880 раз в сутки. Плюс UDP STUN-проба каждые 30 с
при наличии второго UDP-носителя. Это ровно то «постоянно опрашивает», но на
**десктопе/GUI**, а не на телефоне: Android-движок (`internal/transport/android`)
этот цикл не использует — у него только реактивный cooldown носителей.

**Что делать:** keep-alive + таймаут 5 с вместо нового клиента на каждую пробу,
интервал 30 с → 60 с при неизменном состоянии. Даёт −50…−90 % handshake'ов.

## 3. Что проверено и в порядке (не трогать)

- **Нет `AlarmManager`, `JobScheduler`, wake-lock'ов** — приложение не будит
  устройство, когда сервис не нужен.
- **Нет поллинга в фоне**: телеметрия и рендер журнала живут только при
  `resumed` и только на своей вкладке.
- **Автопроверка обновлений — 12 ч** (`UpdateChecker.THROTTLE_MS`), один запрос
  к `api.github.com` за период. В замер 1 Гц/2 % не входит.
- **Логи ограничены** 1000 строками (`LogBuffer.MAX_LINES`), дубликаты внутри
  5 с схлопываются (`relayLogWriter`, `relayDupWindow`).
- **Нет периодических DNS/HTTP-запросов на Android** — ни в `mobile/`, ни в
  `internal/transport/android` нет тикеров с сетевой активностью.

## 4. Порядок работ (если делать)

| # | Что | Ожидаемый эффект | Риск |
|---|---|---|---|
| 1 | `default: direct` + явные TUNNEL-зоны на Android (как в десктопной политике) | снимает с туннеля весь фоновый трафик ОС — десятки соединений/мин | средний: политика меняет маршрутизацию, нужен прогон на устройстве |
| 2 | Мультиплексирование VLESS (mux) | −60…−80 % TLS-handshake'ов на активном трафике | требует поддержки mux на VPS |
| 3 | Фильтр уровня журнала (P3) | меньше аллокаций/GC, чище журнал | низкий |
| 4 | `gcTick` 1 с → 5 с (P4) | −80 % пробуждений планировщика | низкий |
| 5 | Поллинг статуса 2 с + лёгкий статус (P2) | −1 % ядра на открытом экране | низкий |
| 6 | Keep-alive для health-маркера (десктоп, P5) | −50…−90 % проб handshake | низкий |

Пункты 3–6 — независимые, маленькие и безопасные. Пункты 1–2 дают основной
выигрыш по батарее и стабильности, но меняют поведение сети, поэтому их надо
делать с замером до/после на этом же устройстве.
