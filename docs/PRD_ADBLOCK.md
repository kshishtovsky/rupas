# PRD: блокировщик рекламы в ядре rupas (Android)

**Версия:** 1.0 · **Дата:** 2026-10-28 · **Статус:** draft for review
**Владелец продукта:** владелец rupas · **Аналитик:** Hermes
**Репозиторий:** `E:\rupas` (монорепо), ветка `master`, коммит-база `6b011f3` (релиз Android 0.3.1)
**Объект анализа:** `mobile/` (gobind-контракт), `internal/transport/android/*` (TUN-транспорт, правила, DNS, peek), `android/app/src/main/java/ru/rupas/android/*` (UI, настройки)
**Этап:** 1 из 3 — требования и варианты решения. System Design и декомпозиция — этап 2. Реализация — этап 3.

---

## 1. TL;DR

1. Бизнес-цель: у пользователя (в сценарии владельца — мать, телефон на мобильном интернете и Wi-Fi) **нет рекламы** в приложениях и при скроллинге сайтов, без потери скорости и без поломки обычных сайтов.
2. Инфраструктура для этого в коде **уже есть** на 80 %: DNS-перехват в TUN (`serveDNS53`), разбор DNS-запроса (`dns4Response`), SNI из ClientHello (`peekClientHello`), таблицы доменов с `ActionBlock` (`rules.go`), загрузка списков с зеркал (`internal/geoip`).
3. Замеры (см. §7): матчер по 41 654 реальным рекламным доменам = **31,7 ns на попадание / 43,8 ns на промах, 0 аллокаций**; компиляция списка **5 ms**, таблица **≈2–3 MB**. Это не влияет ни на скорость, ни на батарею.
4. Покрытие P0 (DNS-синкхол + SNI-блок): баннеры/интерстишиалы в приложениях, веб-реклама на сайтах, трекеры — **да**. Реклама в приложении YouTube (pre/mid-roll) — **нет, и на сетевом уровне не будет** (§4, §6).
5. P2 (локальный CA + MITM, opt-in) расширяет покрытие до URL-уровня (реклама в Chrome/Firefox, часть нативной рекламы), но требует установки сертификата и даёт риск поломки приложений с pinning.
6. Итого: 27 функциональных требований (`FR-1…FR-27`), 12 нефункциональных (`NFR-1…NFR-12`), 4 варианта архитектуры с вердиктами, 3 этапа с гейтами.
7. Заблокированы решениями владельца: 6 вопросов в §13 (главный — обещаем ли «YouTube без рекламы» в продуктовой коммуникации).

## 2. Проблема

### 2.1 Сценарий, который ломается

1. Пользователь открывает приложение (игра, новостник, соцсеть) — видит баннер, интерстишиал на весь экран, видео-вставку.
2. Открывает сайт в браузере, скроллит — межстрочная реклама, «промо-блоки», всплывающие окна.
3. Смотрит YouTube — pre-roll и mid-roll реклама.
4. Ожидание: «я платил за то, чтобы этого не было / приложение обещает “тихий обход”, пусть убирает и рекламу».
5. Факт: rupas сегодня фильтрует только маршрут (туннель/напрямую/блок) и не фильтрует **содержимое запросов**. Реклама идёт либо напрямую, либо через туннель — как обычный трафик.

### 2.2 Почему это отдельная задача, а не «ещё одно правило маршрутизации»

Существующий `ActionBlock` в ядре блокирует поток **по IP/SNI**, но:
- не отвечает на DNS-запросы (приложение получает настоящий IP, потом получает отказ в соединении — часть SDK это переживает и повторяет с другого домена);
- не смотрит на имя в DNS вообще;
- не умеет списков рекламы (только то, что вписал пользователь вручную в экране «Маршруты»).

### 2.3 Механизмы (AS-IS, с точками в коде)

| # | Механизм | Где | Видимый эффект |
|---|----------|-----|----------------|
| A1 | DNS-запросы уходят в TUN и релеятся как обычный UDP; подмены ответа нет | `internal/transport/android/tun.go::serveDNS53` (вызывается только при `preferIPv4 && dst.Port()==53`), `relayUDP` | приложение получает настоящий IP рекламного домена |
| A2 | Разбор DNS уже реализован, но только для AAAA-фильтра | `internal/transport/android/dns4.go::dns4Response` | кодек есть, ветки «имя в списке» нет |
| A3 | SNI читается из ClientHello и попадает в `FlowMeta` | `internal/transport/android/peek.go::peekClientHello`, `engine.go::decide` | можно блокировать по имени — но только по правилам, вписанным руками |
| A4 | Таблица доменов и `ActionBlock` есть | `internal/transport/android/rules.go` (`sniExact`/`sniWild`, `defaultAction`), `engine.go::dialEgress` → `errFlowBlocked` | блок работает, списков нет |
| A5 | Списки скачивать умеем (geoip, зеркала, кэш в `filesDir`) | `internal/geoip/geoip.go` + `rules.go::loadGeoTables` | переиспользуется для списков рекламы |
| A6 | Настройки идут из Java JSON-ом с жёсткой валидацией неизвестных полей | `internal/transport/android/settings.go::ParseSettings` (`DisallowUnknownFields`) | новое поле `adblock` надо добавить явно, иначе `setSettings` упадёт |
| A7 | UI настроек — одноэкранная форма с чекбоксами | `android/.../SettingsActivity.java`, `res/layout/activity_settings.xml` (`cbFallback`) | тумблер встраивается по образцу `cbFallback` |
| A8 | QUIC (udp:443) заблокирован дефолтным пресетом | `rules.go::DefaultRules` (`{Ports:"443", Proto:udp, Action:Block}`) | браузеры уже ходят по TCP → фильтр по имени увидит соединение |

**Что работает и ломать нельзя (инварианты):**

- `I-1` честность статуса туннеля (`tunnel`/`tunnel_detail` в `Status()`) — из 0.3.1;
- `I-2` приоритет per-app правил над всеми остальными стадиями (`engine.go::appAction`);
- `I-3` RU-зоны и `geoip:ru` → DIRECT (иначе ломается доступ к российским сайтам);
- `I-4` `preferIPv4`: AAAA → пустой NOERROR, v6-потоки дропаются;
- `I-5` нулевые аллокации в hot path (`internal/transport/android/*` — гейт в бенчах);
- `I-6` `Settings` валидируется целиком: неизвестное поле = отказ `setSettings` (значит Java и Go обязаны обновиться вместе).

## 3. Цели и метрики

| ID | Бизнес-требование | Как измеряем | Цель |
|----|-------------------|--------------|------|
| BR-1 | Пользователь не видит баннерной/интерстишиальной рекламы в приложениях | ручной чек-лист из 10 приложений (мессенджер, новостник, 2 игры, файлообменник, погода, 2 магазина, браузер, видеоплеер) до/после | ≥ 8 из 10 без баннеров |
| BR-2 | Реклама на сайтах при скроллинге отсутствует | чек-лист 10 сайтов (RU + глобальные) в Chrome | ≥ 8 из 10 без рекламных блоков |
| BR-3 | Обычные сайты и приложения не ломаются | тот же чек-лист: логин, оплата, видео, карты должны работать | 0 регрессий на 10 сайтах |
| BR-4 | Скорость не падает | `speedtest` до/после на одном APN/Wi-Fi; время загрузки 5 сайтов (p50) | дельта ≤ 3 % |
| BR-5 | Батарея не страдает | `adb shell dumpsys batterystats` за 30 мин активного экрана | дельта ≤ 5 % |
| BR-6 | Пользователь понимает, что фильтр работает | счётчик «заблокировано» + состояние `on/off/failed` в UI | виден на главном экране |

**North Star (продукт):** «тихий интернет» — состояние, в котором на телефоне пользователя за сессию не отрисовано ни одного рекламного блока, при этом ни один нужный сайт не сломался. Термин «рекламный блок» определён чек-листами BR-1/BR-2, а не ощущением.

**Вне области (явно, чтобы дизайн не расползался):**

- косметическая фильтрация (скрытие элементов страницы) — требует движка в браузере, не в ядре;
- антифингерпринтинг, анти-трекерная аналитика как отдельный продукт;
- родительский контроль, блокировка «взрослого» контента;
- блокировка рекламы в Telegram (спонсорские сообщения идут с того же DC, что и сообщения — сетевой слой их не отличает);
- iOS, десктоп-GUI (та же логика позже переиспользуется, но в этом PRD не планируется);
- обход блокировок как таковой (это существующий продукт, не трогаем).

## 5. Слои блокировки и честная матрица покрытия

`L0` DNS-синкхол · `L1` SNI-блок (TLS) · `L2` Host/URL (открытый HTTP) · `L3` MITM + URL-правила · `L4` модификация клиента (вне ядра)

| Тип рекламы | Механизм доставки | L0 | L1 | L2 | L3 | L4 | Вердикт |
|---|---|---|---|---|---|---|---|
| Баннеры/интерстишиалы в приложениях (AdMob, AppLovin, Unity Ads, Vungle, ironSource, Facebook Audience) | отдельные домены SDK | ✅ | ✅ | — | ✅ | — | **закрывается в P0** |
| Веб-баннеры на сайтах (doubleclick, adfox, an.yandex.ru, adriver) | сторонние домены | ✅ | ✅ | ✅ | ✅ | — | **закрывается в P0/P1** |
| Трекеры/аналитика (app-measurement, google-analytics, facebook pixel) | сторонние домены | ✅ | ✅ | ✅ | ✅ | — | **закрывается в P0** |
| Реклама, отдаваемая с того же домена, что и контент (нативная, «промо» внутри ленты) | первый домен | ❌ | ❌ | ❌ | ⚠️ частично (URL-правила) | ✅ | **только L3/L4** |
| Реклама в приложении YouTube (pre/mid-roll) | тот же `googlevideo.com`, что и видео; серверная вставка в поток | ❌ | ❌ | ❌ | ⚠️ не гарантируется (H-1) | ✅ (патч клиента) | **не обещаем** |
| YouTube в браузере (Chrome Android) | `youtube.com` + `googlevideo.com` | ❌ | ❌ | ❌ | ⚠️ частично, зависит от H-1 | — | **частично, P2** |
| Спонсорские сообщения Telegram | тот же DC, что и сообщения | ❌ | ❌ | ❌ | ❌ | ✅ (клиент) | **вне области** |
| Реклама в приложениях с certificate pinning | — | ✅ (если домен отдельный) | ✅ | — | ❌ (MITM невозможен) | — | **только P0/P1-слоями** |

Легенда: ✅ работает · ⚠️ работает частично/не гарантировано · ❌ не работает · — неприменимо.

**Почему L0 (DNS) — основной слой, а не L1:** DNS-ответ приходит один раз на домен, приложение получает `0.0.0.0`, `connect()` падает мгновенно, лишних TCP-соединений не возникает вообще. L1 нужен как страховка: (а) приложения с захардкоженными IP, (б) устройства с Private DNS (DoT/DoH) в обход нашего DNS, (в) домены, закэшированные до включения фильтра.

**Почему YouTube-приложение — «нет»:** рекламный и обычный видеопоток приходят с одного хоста (`*.googlevideo.com`), отличаются только параметрами подписанного URL; блокировка хоста убивает видео целиком. Серверная вставка рекламы в поток (SSAP) означает, что даже URL-фильтрация не всегда видит границу «реклама/контент». Проверка гипотезы — §7.4.

## 6. Варианты решения

| # | Вариант | Что даёт | Стоимость | Риски | Вердикт |
|---|---------|----------|-----------|-------|---------|
| **A** | Только DNS-синкхол, список в APK | баннеры в приложениях, веб-реклама | 3–4 дня | DoT/DoH и захардкоженные IP обходят; списки стареют | база для P0 |
| **B** | **DNS-синкхол + SNI-блок, список в APK** | A + ловит DoH/захардкоженные IP | 5–7 дней | чуть выше риск ложных срабатываний | **рекомендуется, P0** |
| **C** | B + локальный DNS-сервер для всего устройства (вне VPN) | работает без VPN | 8–10 дней | требует `VpnService`-less подхода (Android Private DNS / локальный резолвер) — на Android без root не решается чисто; ломает модель продукта | отклонено |
| **D** | **B + MITM (локальный CA, opt-in)** | URL-уровень: реклама в Chrome, часть нативной, «промо»-блоки | 15–20 дней | установка сертификата вручную; приложения с pinning ломаются (банки!); +1 TLS-хендшейк на домен по CPU, риск падения скорости; юридически ближе к «вмешательству в трафик» | **P2, за флагом, по умолчанию off** |
| **E** | Взять sing-box rule-set (`.srs`) вместо своего формата | готовые конвертеры списков, меньше своего кода | 4–6 дней | тянет `sing-box/rule-set` + `geosite` в AAR (размер), формат бинарный → нельзя править на телефоне; для DNS-слоя всё равно нужен свой ответ | отклонено для P0, пересмотреть при P1 |
| **F** | Свой DoH-резолвер на VPS с фильтрацией | централизованные списки, статистика | 6–8 дней + сервер | задержка DNS +30–60 ms, зависимость от одного сервера, приватность (видно все домены пользователя) | отклонено: противоречит «тихому» продукту |
| **G** | Патч YouTube-клиента (ReVanced-подход) | единственный способ убить видео-рекламу | вне ядра | юридические риски, поддержка форков, не наш продукт | вне области, упомянуть в инструкции |

**Рекомендация:** P0 = вариант **B** (сразу, без MITM). P1 = пайплайн списков + per-app + whitelist UI. P2 = вариант **D** за явным opt-in с предупреждением и дефолтным whitelist банковских/гос-приложений.

## 7. Проверка гипотез (замеры, не рассуждения)

### 7.1 P-1: стоимость матчера на hot path — **подтверждено, дёшево**

Способ: суффиксное множество FNV-1a хешей (полное имя + каждый родительский домен), 120 000 синтетических доменов, `testing.B` на Ryzen 9 7950X3D, Go 1.26:

```
BenchmarkMatchHit   3000000   31.67 ns/op   0 B/op   0 allocs/op
BenchmarkMatchMiss  3000000   43.80 ns/op   0 B/op   0 allocs/op
TestNoAlloc: 0.0 allocs per lookup на всех реальных именах
```

Вывод: на ARM-ядре телефона ожидаем 100–250 ns — на 4–5 порядков меньше одного RTT (20–80 ms). Требование `I-5` выполнимо без трюков: матчер работает по `[]byte` (имя из DNS-пакета и SNI из peek-буфера), без `string`.

### 7.2 P-2: реальность списков — **подтверждено, но с оговоркой**

Источники (скачаны через зеркало `gcore.jsdelivr.net`, `raw.githubusercontent.com` на этой машине блокируется провайдером):

| Файл | Размер | Годных доменов |
|------|--------|----------------|
| EasyList `easylist_adservers.txt` | 914 KB | 41 232 строки `||domain^` |
| AdGuard `BaseFilter/adservers.txt` | 37 KB | 1 279 |
| AdGuard DNS filter (`HostlistsRegistry/assets/filter_1.txt`) | 4,45 MB | 4 398 |

Объединение, после нормализации: **41 654 уникальных домена**, из них
`$`-модификаторы у **5 160** правил, из которых **5 111 безопасно отбрасываются** (`third-party`, `popup`, `document`, `all`, `important`) и только **49** отбрасываются совсем (`domain=`, `denyallow=`, `method=`); **5 218** строк — не домены (regex, косметика) и игнорируются.
Компиляция: **5 ms**, **4,42 MB аллокаций** за сборку таблицы (живая таблица ≈2–3 MB).

**Оговорка (важно для ожиданий):** списки ad-servers **не содержат** `pagead2.googlesyndication.com` — uBlock ловит его URL-правилом, а не DNS. То есть DNS-слой закрывает длинный хвост рекламных сетей, но не «всё, что видит uBlock». Это ещё один аргумент за P2/MITM как расширение, и за то, чтобы **не обещать в UI «рекламы нет вообще»**.

### 7.3 P-3: что реально летит с её телефона — **данные из лога 0.3.1**

Лог `rupas-logs-20261028-012951.log` (1000 строк, полный кольцевой буфер): 100 ClientHello, **22 уникальных SNI**, среди них ни одного рекламного домена: `pubsub.googleapis.com`, `sdkconfig.ad.rus.xiaomi.com`, `www.google.com`, `dns.google.com`, `youtubei.googleapis.com`, `yt3.ggpht.com`, `redirector.googlevideo.com`, `people-pa.googleapis.com`, `speechs3proto2-pa.googleapis.com`, `meetings.googleapis.com`.

Вывод: на её профиле рекламный трафик почти целиком **внутри приложений, которые уже ходят на свои домены** (Google/YouTube/Xiaomi). Значит P0 даст ей заметный, но не полный эффект: баннеры сторонних SDK уйдут, видео-реклама в YouTube — нет (§5). Это надо сказать ей прямо, иначе «не сработало» будет воспринято как баг.

### 7.4 H-1: «MITM + URL-правила убивают рекламу в YouTube» — **не проверено, требует устройства**

Проверка (после P2, на живом телефоне): включить MITM, смотреть в журнале `adblock: url=…youtube.com/api/stats/ads`, `…/get_midroll_info`, `…/pagead/`; проиграть 10 видео, посчитать pre-roll. Критерий: если при заблокированных URL-правилах pre-roll остаётся — работает SSAP, и вариант D не закрывает YouTube даже в браузере. До проверки в UI и в обещаниях YouTube не упоминаем.

## 8. Функциональные требования

### 8.1 Слой L0 — DNS

- **FR-1.** Ядро перехватывает **все** UDP/53 сессии в TUN (сейчас — только при `preferIPv4`), независимо от настроек адресации.
- **FR-2.** Для A/AAAA-запроса имя нормализуется (lower-case, без завершающей точки) и проверяется по таблице блокировки; при попадании ядро **само** синтезирует ответ: `A → 0.0.0.0`, `AAAA → ::`, TTL 60 s, `RA=1`, `RCODE=0`, копия question-секции (совместимо с `dns4Response`).
- **FR-3.** Ответ синтезируется в буфер из существующего пула (`buf.NewPacket`) — без аллокаций на запрос.
- **FR-4.** Не-A/AAAA запросы (HTTPS/SVCB, MX, TXT) для заблокированного имени → `NXDOMAIN` (чтобы не подсказывать клиенту альтернативный адрес через HTTPS-записи).
- **FR-5.** Все остальные запросы релеятся прозрачно, как сейчас (никакой смены резолвера: приватность и совместимость).
- **FR-6.** Счётчик `adblock_hits_dns` инкрементируется один раз на заблокированный запрос, раз в N счётчик отдаётся в `Status()`.

### 8.2 Слой L1 — SNI

- **FR-7.** После `peekClientHello` имя проверяется по таблице блокировки **до** решения о маршруте: попадание → `ActionBlock`, поток не открывается (`errFlowBlocked`), счётчик `adblock_hits_sni`.
- **FR-8.** Порядок приоритетов: per-app правило (`I-2`) → **adblock** → пользовательские правила «Маршруты» → пресет. Пользовательское правило для конкретного домена **переопределяет** adblock (явное действие пользователя сильнее эвристики).
- **FR-9.** Если домен в whitelist (`@@||domain^` или «разрешить» из журнала) — блокировка не применяется ни в L0, ни в L1.

### 8.3 Слой L2 — открытый HTTP (P1)

- **FR-10.** Для TCP:80 поток читается до `Host:` (ограничение 4 KB, таймаут 2 s — как у peek), имя проверяется по той же таблице; попадание → отдать `403` локально и закрыть, не открывая исходящее соединение.

### 8.4 Списки

- **FR-11.** В APK поставляется встроенный список (нормализованное объединение EasyList adservers + AdGuard adservers + AdGuard DNS filter, отфильтрованное по §7.2), формат — один домен на строку, `#` комментарий.
- **FR-12.** Поддерживаемые входные форматы при импорте/обновлении: hosts (`0.0.0.0 domain`), ABP-подмножество `||domain^` и `@@||domain^`, с отбрасыванием `$`-модификаторов из безопасного набора (§7.2) и подсчётом отброшенных в отчёт импорта.
- **FR-13.** Обновление списков — с зеркал (переиспользовать схему `internal/geoip`: цепочка зеркал, таймаут, атомарная установка файла в `filesDir`), проверка целостности (размер + количество строк в коридоре), отказ от установки битого файла.
- **FR-14.** Списки читаются при старте транспорта (как правила в `settings.Rules`), изменение списка требует перезапуска VPN — существующая семантика, новых «горячих» путей не вводим.
- **FR-15.** Пользовательский whitelist и персональные «разрешить» хранятся в настройках и применяются поверх любого списка.

### 8.5 Настройки и контракт

- **FR-16.** В JSON `setSettings` добавляется объект `adblock`: `{"enabled":bool,"lists":["builtin","file:/…","url:…"],"whitelist":["a.com","*.b.com"],"update":true}`. Поле необязательное; отсутствие = фильтр выключен (обратная совместимость — старый APK/старый AAR работают как раньше).
- **FR-17.** `Status()` расширяется: `adblock` (`off|on|failed`), `adblock_detail` (причина), `adblock_domains` (размер таблицы), `adblock_hits_dns`, `adblock_hits_sni`. По образцу честного `tunnel` из 0.3.1: если список не загрузился — `failed` + причина, а не тихое `on`.
- **FR-18.** В `Settings.Validate` — валидация `adblock`: неизвестный префикс источника, пустой домен, домен с пробелом/`/` → отказ с индексом элемента (как в `app_rules`).
- **FR-19.** Логирование: одна строка на блокировку в debug-режиме (`adblock: <domain> (dns|sni|http, list)`) и агрегированный счётчик в info. Никаких логов на каждый пакет (§I-5).

### 8.6 UI

- **FR-20.** Тумблер «Блокировать рекламу» в «Настройках» (по образцу `cbFallback`), сохраняется в `SettingsStore` и уезжает в `toJson()`.
- **FR-21.** На главном экране — счётчик «Заблокировано: N» (сумма хитов) и состояние фильтра: `on` / `off` / `failed: <причина>` (по `adblock_detail`), рядом с честным статусом туннеля.
- **FR-22.** Журнал: кнопка «Разрешить» на строке блокировки → домен попадает в whitelist, VPN перезапускается (`ACTION_RESTART`), строка подтверждается тостом.
- **FR-23.** В настройках — «Обновить списки» с прогрессом/ошибкой текстом (без диалога-«висит»).

### 8.7 Наблюдаемость и отладка

- **FR-24.** `testRoute` в приложении дополнительно показывает, попал ли домен в adblock-таблицу и из какого источника (builtin/user).
- **FR-25.** В журнал при старте — одна строка: `adblock on: 41 654 domains (builtin), whitelist 3` или `adblock failed: <причина>`.

### 8.8 Продуктовые ограничения (обязательные тексты)

- **FR-26.** В UI рядом с тумблером — короткая сноска: «Блокируются рекламные сети. Реклама внутри приложения YouTube и спонсорские сообщения Telegram сетью не отключаются». Это исполнение §5 и защита от «не сработало».
- **FR-27.** Ни в одном тексте продукта нет обещания «рекламы нет вообще» — только «рекламные сети блокируются».

## 9. Нефункциональные требования

- **NFR-1.** Hot path без аллокаций: матчер по `[]byte`, 0 allocs/op (гейт в тесте, как в `TestNoAlloc`); замер: ≤ 60 ns/op на x86, ≤ 250 ns/op на ARM.
- **NFR-2.** Память: таблица 41–45 тыс. доменов ≤ 4 MB с учётом роста map; список 90 тыс. — ≤ 8 MB.
- **NFR-3.** Время старта: компиляция списка ≤ 50 ms на телефоне (x86-замер 5 ms).
- **NFR-4.** Задержка: DNS-блок не добавляет RTT (локальный ответ); SNI-блок уменьшает время до отказа.
- **NFR-5.** Батарея: ни одного нового таймера/горутины на поток; фоновая проверка обновлений — не чаще 1 раза в 24 ч.
- **NFR-6.** Размер APK: встроенный список ≤ 1,5 MB raw (сжатие в APK ~0,3 MB).
- **NFR-7.** Оффлайн: фильтр полностью работает без сети со встроенным списком.
- **NFR-8.** Приватность: ни один домен пользователя не уходит на наши серверы; обновление списков — только GET статического файла, без идентификаторов.
- **NFR-9.** Совместимость контракта: отсутствие `adblock` в JSON = выключенный фильтр; старый AAR + новый APK и наоборот не должны падать (`CoreBridge` уже резолвит методы по контракту).
- **NFR-10.** Идемпотентность: повторное применение настроек/перезапуск не дублирует таблицы и не течёт (проверка `HeapAlloc` до/после 10 перезапусков).
- **NFR-11.** Отказоустойчивость: битый/отсутствующий список ≠ падение ядра: `adblock failed` + трафик идёт как раньше.
- **NFR-12.** Безопасность: списки — данные, не код; парсер не паникует на мусоре (fuzz-тест 10 мин на каждом релизе).

## 10. Данные, формат и пайплайн списков

```
источник (jsdelivr-зеркало)
   │  GET (таймаут 20 s, 3 зеркала по очереди)
   ▼
parse: hosts | ||domain^ | @@||domain^   ──► отброшено: regex, косметика, domain=/denyallow=
   │                                          (счётчик отброшенных в отчёт)
   ▼
normalize: lower-case, punycode as-is, дедуп, лимит 200 000 доменов
   │
   ▼
filesDir/adblock.txt  (атомарная замена через .tmp + rename)
   │
   ▼
compile при Start → map[uint64]struct{} (FNV-1a суффиксы) + whitelist отдельным множеством
```

- Встроенный список в APK: `assets/adblock.txt`, при первом запуске копируется в `filesDir` (только если файла нет).
- Обновление — только по явному действию или раз в сутки, при `update:true`.
- Формат хранения простой (plain text) намеренно: пользователь может открыть, посмотреть, дописать. Бинарные форматы (`.srs`) отклонены в P0 (вариант E).

**Источники (по состоянию на 2026-10-28, доступность проверена):**

## 12. Тест-план

**Юнит (Go, обязательные):**
1. парсер: hosts, `||domain^`, `@@`, `$third-party`, regex/косметика → отброшены; мусор не паникует (fuzz);
2. суффиксный матчер: `ads.example.com` ловится правилом `example.com`; `notexample.com` — нет (границы меток);
3. DNS-синтез: A→`0.0.0.0`, AAAA→`::`, TTL, RCODE, question эхом; EDNS-запрос не ломается;
4. приоритеты: per-app → adblock → пользовательское правило → пресет (табличный тест, как в `rules_test.go`);
5. whitelist: `@@||doubleclick.net^` отменяет блокировку и в DNS, и в SNI;
6. `0 allocs/op` на матчере и на синтезе ответа (гейт, как `TestNoAlloc`);
7. `Settings.Validate`: невалидный `adblock` → отказ с индексом; отсутствие поля → фильтр выключен;
8. битый файл списка → `adblock failed`, транспорт продолжает работать.

**Интеграция (живой телефон, `install -r`):**
9. `adb logcat -d -s RupasVpn:V` содержит `adblock on: N domains` при старте;
10. `Status()` в UI: счётчик растёт после открытия приложения с рекламой, `tunnel` не пострадал;
11. чек-листы BR-1/BR-2/BR-3 до/после (фиксировать скриншотами);
12. `speedtest` и `dumpsys batterystats` (BR-4, BR-5);
13. 10 перезапусков VPN → `HeapAlloc` не растёт (NFR-10).

**Регрессия существующего:** `go build ./...`, `GOOS=linux go build ./internal/transport/android/ ./mobile/`, `go test ./internal/transport/android/...`, живой тест туннеля 0.3.1 (VLESS+Reality + hysteria2), инварианты `I-1…I-6`.

## 13. Риски и открытые вопросы

### Риски

| ID | Риск | Вероятность | Влияние | Что делаем |
|----|------|-------------|---------|-----------|
| R-1 | Ложное срабатывание ломает нужный сайт (CDN/логин/оплата) | средняя | высокое (BR-3) | whitelist «в один тап» из журнала; отдельный список «хрупких» доменов (банки, госуслуги, оплата) в whitelist по умолчанию |
| R-2 | Private DNS (DoT/DoH) на телефоне обходит L0 | высокая | среднее | L1 как страховка; в UI подсказка «для полного эффекта отключите Private DNS» |
| R-3 | Ожидание «нет рекламы в YouTube» не выполнено → воспринимается как баг | высокая | высокое | FR-26/FR-27: честный текст в UI; не обещать в продукте |
| R-4 | Списки стареют / зеркала недоступны в РФ | высокая | среднее | встроенный список + цепочка зеркал + ручной импорт файла |
| R-5 | MITM (P2) ломает приложения с pinning | высокая | высокое | opt-in, off по умолчанию, per-app исключения, дефолтный whitelist банков/госуслуг |
| R-6 | Размер AAR/APK растёт | низкая | низкое | список в assets, не в коде; лимит NFR-6 |
| R-7 | `DisallowUnknownFields` ломает совместимость при рассинхроне APK/AAR | средняя | высокое (VPN не стартует) | поле необязательное, версия контракта в `Status()`, порядок релиза: AAR → APK в одном коммите |

### Открытые вопросы (нужны решения владельца до этапа 2)

1. **Фильтр по умолчанию включён или выключен?** Рекомендация: включён (иначе «не работает»), whitelist правится.
2. **Обещаем ли YouTube?** Рекомендация: нет, только текст FR-26. Иначе риск R-3.
3. **P2 (MITM) вообще в плане?** Если да — предупреждение о сертификате и whitelist банков надо проектировать уже в P0 (место в настройках).
4. **Свой список или сторонние?** Рекомендация: сторонние + свой «хрупкий» whitelist; собственный курируемый список — только если понадобится RU-специфика (Яндекс/VK-реклама).
5. **Есть ли VPS для зеркала списков?** (у нас есть `82.146.52.225` / `62.109.11.78`) — рекомендация: положить нормализованный список туда, чтобы обновление не зависело от jsdelivr.
6. **Логировать ли заблокированные домены локально?** Рекомендация: да, только в кольцевом буфере журнала (1000 строк), никуда не отправлять.

## 14. Приложения

**A. Почему DNS-ответ `0.0.0.0`, а не `NXDOMAIN`.** `0.0.0.0` даёт мгновенный отказ `connect()` (EADDRNOTAVAIL/EHOSTUNREACH) — приложения не ждут таймаут; `NXDOMAIN` часть SDK воспринимает как «DNS сломан» и уходит на захардкоженный IP или на резервный домен. Компромисс: A/AAAA → нули, остальные типы (HTTPS/SVCB) → `NXDOMAIN`, чтобы клиент не получил альтернативный адрес.

**B. Почему не блокируем по IP.** Рекламные сети сидят на общих CDN (Google, Cloudflare, Akamai): блокировка IP-диапазона убьёт обычный контент. Единственное исключение — уже существующие Telegram-CIDR (TUNNEL), их не трогаем.

**C. Почему список читается при старте, а не «на лету».** Совпадает с существующей семантикой правил (`settings.Rules` читаются в `Start`, изменение → `ACTION_RESTART`). Горячая замена таблицы потребовала бы RCU/atomic-swap и новых тестов на гонки — цена выше выгоды (NFR-10).

**D. Ссылки на код, использованные в анализе.**
