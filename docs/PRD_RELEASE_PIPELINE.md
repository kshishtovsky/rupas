# PRD: релизный конвейер и автообновление Rupas

Статус: черновик на согласование · Версия 1.0 · 2026-10-28
Затрагивает: `android/`, `cmd/rupas-gui`, `cmd/rupasd`, `.github/`, README

---

## 1. Бизнес-проблема

Rupas устанавливается вручную: APK и архив с Windows-сборкой передаются
«из рук в руки» (мессенджер, файлообменник). Следствия:

1. **Установка — ручная операция на каждой стороне.** Владелец собирает и
   отправляет файл, получатель ищет его, скачивает, ставит, разбирается с
   «разрешить установку из неизвестных источников».
2. **Обновлений де-факто нет.** Пользователь остаётся на той версии, которую
   ему когда-то прислали. Багфиксы и правки маршрутизации не доезжают.
3. **Нет канала доверия.** APK без подписи и контрольных сумм невозможно
   отличить от подменённого.
4. **Нет публичной точки входа.** Проект нельзя показать, у него нет
   README, релизов, истории изменений — невозможно «просто дать ссылку».

### Цель

Один публичный адрес репозитория закрывает весь цикл «получить → обновить»:

> дать ссылку на репозиторий, остальное приложение делает само.

### Метрики успеха

| Метрика | Цель |
|---|---|
| Ручных действий для установки нового пользователя | 2 (открыть Release → скачать APK) |
| Ручных действий для обновления существующего | 0 (приложение само предлагает) |
| Время от коммита в `dev` до доступного обновления | ≤ 15 минут (CI) |
| Артефакты с проверяемой подписью/хэшем | 100% релизов |
| Проверка обновлений без сети/при ошибке API | Не мешает работе, ≤ 1 диалога |

## 2. Пользователи и сценарии

**P1. Владелец (мейнтейнер).** Пушит в `dev`, мёржит в `master`. Хочет:
релиз без ручной сборки, версия не забывается, артефакты одинаковые у всех.

**P2. Друг-пользователь (Android).** Поставил APK полгода назад. Хочет: при
запуске увидеть «есть версия 0.7.0 → обновить», нажать одну кнопку.

**P3. Друг-пользователь (Windows).** Пользуется `rupas-gui.exe`. Хочет то же
самое в интерфейсе GUI.

**P4. Случайный посетитель GitHub.** Хочет за минуту понять, что это, как
поставить и что изменилось в последней версии.

### Ключевые сценарии (happy path)

- **S1 Установка:** GitHub → Releases → `Rupas-android-0.7.0-arm64.apk` →
  установка → приложение запускается, показывает версию `0.7.0`.
- **S2 Автообновление Android:** приложение открыто/сервис работает →
  фоновая проверка → доступна 0.7.0 → диалог со списком изменений →
  «Обновить» → скачивание → системный установщик → перезапуск сервиса.
- **S3 Ручная проверка:** Настройки → «Проверить обновления» → либо
  «Установлена последняя версия (0.7.0)», либо диалог из S2.
- **S4 Релиз:** мерж `dev` → `master` → CI считает версию по коммитам →
  собирает 3 артефакта → публикует Release + образ в GHCR → тег `v0.7.0`.

## 3. Границы

**В scope:** создание репозитория и веток, профессиональный README и docs,
CI/CD (сборка + релиз + пакеты), политика версионирования, механизм
проверки/загрузки обновлений в Android и Windows GUI, кнопка ручной проверки.

**Не в scope (v1):** авто-обновление `rupasd` на серверах/роутерах, магазины
приложений (Google Play / Microsoft Store), кодовая подпись Windows (EV-
сертификат), delta-обновления, каналы beta/stable, подписанные метаданные
обновлений (TUF/Ed25519).

## 4. Функциональные требования

### FR-1. Публичный репозиторий и структура веток

- Репозиторий на GitHub-аккаунте владельца, **public** (иначе друзья не
  скачают релизы без авторизации).
- Ветки: `master` — стабильная, только мержи из `dev`, отсюда релизы;
  `dev` — интеграция; `feature/*` — задача. Прямые пуши в `master` закрыты
  branch protection (после появления CI).
- `master` защищена: обязательный зелёный CI (`build` + `test`).
- README, `docs/`, лицензия, `CHANGELOG.md`, шаблоны Issue/PR.

*Приёмка:* клон с нуля собирается по инструкции README; дерево веток
соответствует модели; в репозитории нет секретов и ключей (см. FR-0).

### FR-0 (P0, блокер публикации). Санитария репозитория

Обнаружено при аудите и **обязано** быть устранено до первого `git push`:

1. `android/keystore/rupas-release.jks` и пароли в `android/app/build.gradle`
   находятся в истории git. Публикация = утечка ключа подписи: любой сможет
   выпустить APK, который Android примет как легитимное обновление.
   → ключ убрать из истории, пароли вынести в локальный
   `android/keystore.properties` (gitignored) + GitHub Secrets.
2. `.git` = 448 МБ, в истории блобы до 70 МБ (`out/*.aar`, `dist/*.apk`,
   `build/*.exe`). Публичный клон такого размера — плохой опыт и риск лимитов.
   → вычистить историю от сборок, добавить в `.gitignore`.
3. Проверить, что `configs/rupas.yaml` (uuid/password) не попал в историю.

Перезапись истории стоит ноль, пока репозиторий не опубликован. **Это
единственное окно, чтобы сделать это бесплатно.**

*Приёмка:* `git log --all -- android/keystore` пуст; в истории нет файлов
>10 МБ из `out/`, `dist/`, `build/`; секретов нет в `git grep` по всей истории.

### FR-2. Единый источник версии

- Файл `VERSION` в корне — единственная правда, semver `MAJOR.MINOR.PATCH`.
- Версия попадает в: `rupasd -version`, `rupasctl -version`, GUI (окно
  «О программе»/заголовок), Android `versionName`, имя APK/zip, git-тег,
  заголовок Release, `CHANGELOG.md`.
- Android `versionCode` вычисляется: `MAJOR*10000 + MINOR*100 + PATCH`
  (0.7.0 → 700). Монотонен при любом увеличении любой компоненты.

*Приёмка:* `rupas-gui.exe` и приложение на телефоне показывают одну и ту же
версию, совпадающую с `VERSION` и тегом.

### FR-3. Политика версионирования (жёсткое правило)

Это правило — часть контракта проекта, а не пожелание:

1. **Любое изменение кода, попадающее в `master`, увеличивает версию.**
   Релиз без инкремента версии невозможен: тег собирается из `VERSION`.
2. Типы инкремента задаются Conventional Commits:
   `fix:` → PATCH, `feat:` → MINOR, `BREAKING CHANGE:`/`feat!:` → MAJOR.
   Прочие (`docs:`, `chore:`, `ci:`) версию не двигают и релиза не создают.
3. Если с прошлого тега есть хотя бы один `fix:`/`feat:` — CI обязан
   выпустить релиз; «забыть поднять версию» технически невозможно, потому
   что версию поднимает CI, а не человек.
4. Ручной bump (`make bump MINOR`) остаётся доступным для случая, когда
   версию надо задать явно; ручной bump всегда имеет приоритет.

*Приёмка:* коммит `fix: ...` в `master` → в течение 15 минут появился тег
`vX.Y.(Z+1)` и Release. Повторный запуск CI на том же коммите не создаёт
второй тег (идемпотентность).

### FR-4. CI/CD: сборка и публикация

Триггеры: PR → `dev`/`master` = сборка + тесты (без публикации);
push в `master` = релиз; push тега `v*` = релиз из тега.

Артефакты каждого релиза (все прикреплены к GitHub Release):

| Артефакт | Назначение |
|---|---|
| `Rupas-android-<ver>-arm64.apk` | телефон (release-подпись, arm64-v8a) |
| `Rupas-win64-<ver>.zip` | `rupas-gui.exe` + `rupasd.exe` + `rupasctl.exe` + `WinDivert` + `windivert`/`desync` ассеты |
| `SHA256SUMS.txt` | контрольные суммы всех артефактов |
| Авто-changelog | из Conventional Commits с прошлого тега |

«Пакеты» в терминах GitHub: сборки APK/EXE — это **Releases** (GitHub
Packages не умеет хранить произвольные бинарники). Дополнительно в GHCR
публикуется образ `ghcr.io/<owner>/rupasd:<ver>` для серверного запуска —
это настоящая часть Packages и стоит ~10 строк в workflow.

*Приёмка:* релиз содержит все 4 позиции; `SHA256SUMS.txt` сходится с
фактическими файлами; APK ставится на чистый телефон; zip распаковывается и
GUI запускается без установки.

### FR-5. Проверка обновлений (общая логика)

- Источник истины: `GET https://api.github.com/repos/<owner>/<repo>/releases/latest`
  (публичный, без токена; лимит 60 запросов/час на IP — при 1–2 проверках в
  сутки неактуален).
- Сравнение по semver из `tag_name`; обновление доступно, если
  `latest > current`.
- Вежливость: `If-None-Match` с сохранённым `ETag`; при `304` — не считать
  это ошибкой и не показывать ничего.
- **Частота: не чаще 1 раза в 12 часов** автоматически (требование «раз в
  день-два» с запасом). Отметка последней проверки хранится локально.
- Ручная проверка кнопкой игнорирует троттлинг, но не чаще 1 раза в 60 с.
- Поведение при ошибках: нет сети / 5xx / кривой JSON → тихо, запись в лог,
  никаких модальных окон. Ручная проверка показывает «Не удалось проверить,
  попробуйте позже».

### FR-6. Обновление Android

- Точки входа: (а) при старте приложения, если с прошлой проверки прошло
  >12 ч; (б) кнопка «Проверить обновления» в Настройках; (в) периодическая
  проверка, пока работает VPN-сервис.
- UX: диалог «Доступна версия X» + changelog + кнопки «Обновить» /
  «Позже». Если версия ниже текущей (откат) — не предлагать.
- Загрузка: APK в кэш приложения через `DownloadManager`/поток, прогресс,
  отмена.
- **Проверка подписи обязательна:** скачанный APK принимается только если
  его подпись совпадает с подписью установленного приложения (иначе —
  удалить и сообщить об ошибке). Это защита от подмены файла и от
  случайной публикации чужой сборки.
- Установка: `FileProvider` + `ACTION_VIEW` (package installer) +
  разрешение `REQUEST_INSTALL_PACKAGES`. Перед установкой — остановить
  VPN-сервис, после установки — предложить перезапуск.
- Новых зависимостей не вводим: планировщик — `AlarmManager`/поток сервиса,
  HTTP — `HttpURLConnection`, JSON — `org.json` (всё в SDK).

*Приёмка:* на телефоне с версией N−1 при открытии появляется предложение;
после установки версия на экране «О программе» = новая; при подменённом
APK установка блокируется с внятной ошибкой.

### FR-7. Обновление Windows GUI

- Точки входа: при старте GUI (если >12 ч) и кнопка «Проверить обновления»
  в настройках; плюс пункт в меню «О программе».
- Загрузка `Rupas-win64-<ver>.zip`, проверка `SHA256` из `SHA256SUMS.txt`,
  распаковка в `%LOCALAPPDATA%\Rupas\updates\<ver>\`.
- Применение: подмена `rupas-gui.exe`/`rupasd.exe` на выходе (переименовать
  старый → переместить новый → перезапуск). Если файл занят — предложить
  «обновится при следующем запуске» и запомнить флаг.
- Автоматическая подмена `rupasd.exe` не выполняется, пока демон запущен:
  сначала `rupasctl off`, иначе файл занят.

*Приёмка:* GUI версии N−1 при старте сообщает о N, обновляется и после
перезапуска показывает N; при недоступной сети — молчит.

### FR-8. Презентация репозитория

- README: что это, скриншоты (есть в `dist/*.png`), быстрый старт для
  Android и Windows, таблица возможностей, ссылка на Releases, схема
  архитектуры, бейджи (CI, последний релиз, лицензия, размер).
- `docs/`: PRD, SYSTEM_DESIGN, это PRD, `VERSIONING.md`,
  `RELEASING.md` (как выпустить релиз и что делать при откате).
- `CHANGELOG.md` — генерируется CI, коммитится обратно.
- Статистика: авто-генерируемый блок в README (LOC по пакетам, число
  тестов, размер бинарников, число релизов). Графики — опционально,
  генерируются SVG силами Go stdlib (без новых зависимостей).
- Лицензия: MIT (подтвердить, см. открытые вопросы).

*Приёмка:* сторонний человек по README ставит приложение без вопросов к
автору.

## 5. Нефункциональные требования

- **Не ломать существующее.** Пайплайн проверки обновлений — аддитивный:
  ни один текущий сценарий (VPN, маршрутизация, adblock, TUI) не меняет
  поведение.
- **Горячий путь не трогаем.** Проверка обновлений — фоновый поток раз в
  12 ч; никаких аллокаций в per-packet пути, zero-alloc тесты остаются
  зелёными.
- **Тесты.** Новый код (парсер semver, сравнение версий, выбор ассета,
  проверка SHA256/подписи) покрывается юнит-тестами; гейт — общий уровень
  покрытия репозитория не падает, новый код не ниже 75%.
- **Секреты только в GitHub Secrets:** keystore (base64), пароли к нему.
- **Идемпотентность CI:** повторный прогон на том же коммите не создаёт
  дублей тегов/релизов и не перезаписывает существующий релиз.
- **Время сборки:** полный релиз ≤ 15 минут.

## 6. Технические решения (черновик)

| Область | Решение | Почему так |
|---|---|---|
| Канал обновлений | GitHub Releases API | Бесплатно, без бэкенда, публично, кэшируется CDN |
| Пакеты | GHCR (`ghcr.io/.../rupasd`) | Единственный формат, который Packages реально умеет |
| Версия | `VERSION` + Conventional Commits + auto-tag в CI | Человек не может «забыть» поднять версию |
| Android сборка | `windows`/`ubuntu` runner + `setup-android` + NDK + `gomobile bind` | `aar` требует NDK; кэшируем тулчейн |
| Windows сборка | `windows-latest`, `go build` с тегами `with_utls with_quic` | CGO не нужен, MSVC не требуется |
| APK | `assembleRelease`, подпись из Secrets, `arm64-v8a` | Как сейчас (`abiFilters 'arm64-v8a'`) |
| Проверка обновлений | общий контракт API + две тонкие реализации | Логика одна, UI разный |
| Модуль Go | `github.com/rupas/rupas` → `github.com/<owner>/rupas` (опционально) | Сейчас путь указывает на несуществующий org; менять дешевле до публикации |

## 8. Риски

| Риск | Влияние | Мера |
|---|---|---|
| Утечка release-keystore в публичный git | Критично: подмена APK | FR-0 + Secrets + ротация ключа, если история уже где-то публиковалась |
| Сборка AAR/APK в CI тяжелее локальной (NDK, ~10 мин) | Медленный фидбэк | кэш Gradle/NDK, `android-smoke` как быстрый предварительный гейт |
| GitHub Actions лимиты для приватных/бесплатных аккаунтов | Релизы встанут | публичный репозиторий = безлимитные минуты на стандартных раннерах |
| Обновление «на живом» Windows: файл занят демоном | Пользователь застрял на старой версии | остановка демона перед подменой + флаг «обновиться при старте» |
| rate limit GitHub API при массовых установках с одного IP | Ложные «нет обновлений» | ETag + 12 ч троттлинг + ошибка не блокирует UI |
| Rewrite истории ломает локальные клоны/бэкап | Потеря работы | бэкап-ветка `backup-pre-public-YYYYMMDD` остаётся локально |

## 9. Открытые вопросы (нужно решение владельца)

1. **Имя и владелец репозитория:** `kshishtovsky/rupas` — публичный?
2. **Лицензия:** MIT (рекомендую) / Apache-2.0 / без лицензии (не рекомендую —
   без неё использовать код юридически нельзя).
3. **Переименовать Go-модуль** `github.com/rupas/rupas` → `github.com/<owner>/rupas`?
   Дешево сейчас, дорого потом.
4. **Стартовая версия:** предлагаю `0.6.0` (APK сейчас 0.5.3), тег `v0.6.0`.
5. **Ключ подписи:** оставляем текущий (друзьям не придётся переустанавливать)
   при условии, что он не попал в публичную историю; иначе — новый ключ и
   одноразовая переустановка у всех.
6. **Токен GitHub:** текущему `gh` не хватает скоупа `workflow` (и `write:packages`
   для GHCR) — потребуется `gh auth refresh -s workflow,write:packages`.
