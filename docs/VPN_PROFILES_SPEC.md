## 2. Модель данных профиля

### 2.1 Запись

| Поле | Тип | Источник | Назначение |
|---|---|---|---|
| `id` | String | `UUID.randomUUID().toString()` | стабильный ключ строки UI и результата теста. **Не индекс** (индекс меняется при удалении/перестановке) |
| `link` | String | ввод | исходная share-ссылка как есть, единственный источник правды для ядра |
| `label` | String | `ParseLink.describe(link)` при добавлении, редактируемо позже | показ в карточке |
| `enabled` | boolean | переключатель | участие в dial chain |
| `order` | int | позиция | **не хранится отдельным полем** — порядок = порядок элементов массива (как сегодня у `links`) |

Метаданные для UI (kind / security / transport) **не храним**: они выводятся из `link` тем же `ParseLink.describe()`/разбором схемы. Дублирование вычисляемого поля = рассинхрон после правки ссылки. Если понадобится «vless · reality» отдельной строкой — это `ParseLink`-функция, не поле в prefs.

### 2.2 Где хранится

Тот же `EncryptedSharedPreferences` (`SettingsStore.java:117 FILE = "rupas_secure_settings"`), новый ключ:

```
profiles = [{"id":"…","link":"vless://…","label":"…","enabled":true}, …]
```

Решение — расширить существующий `SettingsStore`, а не заводить `ProfileStore`:
- один владелец файла prefs и один `cachedPrefs` (`SettingsStore.java:133`) — второй store дал бы второй `MasterKey` (в комментарии :130-132 уже зафиксировано, что это дорого по батарее);
- миграция должна читать `K_LINKS` и писать `profiles` атомарно в одном `edit()` — с двумя классами это два раздельных коммита и окно потери данных.

Класс профиля — вложенный `static final class SettingsStore.Profile` (новый файл не нужен).

### 2.3 Миграция `links` → `profiles`

Выполняется в `SettingsStore.load()` до возврата снимка, **один раз, идемпотентно**:

```
если prefs.contains("profiles")  → ничего не делаем (даже если "[]")
иначе если links пуст          → profiles = [] , ключ записать
иначе                          → split("\n") → trim → drop пустых
                               → на каждую ссылку Profile{id=randomUUID, link, label=describe, enabled=true}
                               → order = порядок строк (первая = primary, как было)
                               → писать profiles ОДНИМ edit(); K_LINKS НЕ трогать
```

Обязательные свойства:
- **Идемпотентность** — страж `contains("profiles")`, а не «непустой список»: пользователь с нулём профилей после миграции не должен получать миграцию повторно.
- **Без потери** — `K_LINKS` остаётся записанным (см. §7, откат на старую сборку). Очищать его нельзя.
- **Без сети и без разбора схем** — `ParseLink.describe()` не бросает (возвращает `link` как есть при несовпадении регулярки), значит миграция не может упасть на «странной» ссылке.
- **Порядок сохраняется** — `enabled=true` всем: если бы миграция что-то выключила, у пользователя молча изменилась бы цепочка.
- Дубликаты в `links` не схлопываются (иначе меняется историческое поведение), схлопывание — только для новых добавлений (§4.1).

## 3. Семантика enable/disable

**Выключенный профиль не едет в `links` для ядра.** Он остаётся в списке со своей ссылкой и своим id, но `toJson()` собирает массив только из `enabled`-профилей в их порядке:

```
profiles: [A(en), B(off), C(en)]  →  JSON "links": ["A","C"]  →  dial chain A→C
```

Это единственный вариант, который не требует правок Go: `Endpoints()` и `Validate()` уже работают с массивом, а «дырка» в середине массива (`null`/пустая строка) отклоняется на `settings.go:137`.

### 3.1 Запрещать ли выключение последнего включённого?

**Рекомендация: не запрещать.** Обоснование: при нуле включённых `isConfigured()` (`SettingsStore.java:60`) вернёт `false` ровно как сейчас при пустой конфигурации — ядро стартует с «туннель off», все TUNNEL-потоки честно эскалируют в DIRECT с записью в журнал (это уже существующая семантика, комментарий `mobile/core.go:76`). Запрет потребовал бы нового состояния в UI («последний нельзя выключить»), объяснения пользователю и обработки случая «осталось одно, но оно битое» — цена выше пользы. Вместо запрета — предупреждение в блоке (§6.4).

### 3.2 Что видит пользователь

- Главный экран: `home_gateway` = первый **включённый** профиль (`flattenLegacy` от него, §4.6), а не «первый в списке». При нуле включённых — `home_gateway_none` («Шлюз: напрямую») и `status_tunnel_off`.
- `Status.carriers[]` содержит только включённые профили; индексы карточек ≠ индексы carriers, сопоставление — по позиции в списке включённых (§6.5).
- Переключение **при поднятом VPN** требует перезапуска ядра: `RupasVpnService.restartIfRunning()` (`RupasVpnService.java:108`), ~2 с, как у правил маршрутизации (`routing_apply_caption`). Молча применять нельзя — `SetSettings` при работающем движке отказывает (`mobile/core.go:76`).

## 4. CRUD

Все операции — над списком в памяти `MainActivity`, коммит в `SettingsStore` по кнопке «Сохранить и применить» (как сейчас `saveSettingsForm`, `MainActivity.java:734`). Отложенный коммит сохраняет текущий UX и даёт бесплатный откат: уход с экрана без сохранения ничего не портит.

| Операция | Вход | Поведение |
|---|---|---|
| **Добавить** | paste (клипборд/диалог) или ручная ссылка | `ParseLink.splitInput(raw)` → на каждую ссылку `Profile{new id, enabled=true}` → **append в конец**; дубликат (совпадение `link` побайтово) отбрасывается с тостом «уже есть»; scroll к первой добавленной |
| **Удалить один** | overflow ⋮ карточки | подтверждение `AlertDialog` («Удалить профиль?» + label), затем `remove` по `id`; при поднятом VPN — перезапуск на «Сохранить» |
| **Изменить ссылку** | overflow ⋮ → «Изменить ссылку» | диалог с предзаполненным `link`; на OK — `splitInput` (ровно 1 ссылка), заменить `link`/`label` у того же `id`, `enabled` и позицию сохранить |
| **Переупорядочить** | ▲/▼ в overflow (переиспользовать `carrierButton`, `MainActivity.java:947`) | `swap` соседей по `id`, порядок массива = порядок перебора; без drag-and-drop (новый `ItemTouchHelper`-слой на `LinearLayout` — лишний код, а свайп занят удалением) |
| **Вкл/выкл** | `MaterialSwitch` в карточке | toggle `enabled`, перерисовка карточки, предупреждение если включённых 0 |

### 4.1 Правила добавления

- Пустой ввод → ничего (не ошибка).
- Ни одной валидной ссылки → `import_failed` с текстом `ParseLink` (как сейчас).
- Частично битый ввод (3 ссылки, одна кривая) — **сейчас весь импорт падает**; после переработки — добавляем валидные, битую показываем в тосте (`import_warning`) по одной строке на ссылку, чтобы человек видел, что именно не влезло.
- Дубликат определяется по нормализованной строке (`trim`), не по host:port: два профиля на один сервер с разными `sid`/транспортом — легитимны.

### 4.2 Пустой список

Никакой плоской формы «на всякий случай». Блок показывает empty-state (§6.4) и кнопку «Добавить профиль».

### 4.3 Что делать с legacy-плоской формой

Правило: **плоские поля видны только когда список профилей пуст** (свежая установка / ручной ввод без ссылки). Как только есть хотя бы один профиль:
- блок `etUuid/etServer/etPort/etSni/etPublicKey/etShortId` в `tab_settings` скрывается (`View.GONE` на контейнере);
- при сохранении плоские поля **вычисляются** из первого включённого профиля через `ParseLink.flattenLegacy()` (§4.6).

Так мы не плодим два источника правды и сохраняем единственный сценарий, который плоская форма реально обслуживает: ввод vless-параметров руками, без share-ссылки.

`SettingsActivity.java` + `activity_settings.xml` в рамках этой ветки **удалить** (мёртвый дубль; удаление ещё и снимает один конфликт с adblock — см. §8.3). Если владелец против — оставить как есть, ветка на них не опирается.

### 4.4 Ограничения

- Максимум профилей: 16 (больше не влезает в осмысленный dial chain и в экран; при превышении — тост, а не тихое обрезание).
- Длина ссылки: без ограничения в UI, но `LogBuffer` не должен получать `link` целиком (§9.1).

### 4.5 Инварианты (проверять в `SettingsStore.save()`)

1. `id` уникален в пределах списка; при коллизии — перегенерировать.
2. `link` непустой и проходит `ParseLink`-регулярку; иначе запись отбрасывается (не сохраняем мусор).
3. Хотя бы одна ссылка в массиве для ядра **не** требуется (§3.1).

### 4.6 `flattenLegacy` при сохранении

`saveSettingsForm` после сборки `links` из включённых профилей вызывает `flattenLegacy(firstEnabled)` и пишет поля в `s.uuid/server/port/sni/publicKey/shortId`. Это чинит `updateEndpointInfo()` (§1.4): главный экран показывает тот шлюз, который реально первым в цепочке. При нуле включённых — поля пустые (экран пишет «напрямую»).

## 5. Тест профиля

### 5.1 Что именно проверяем

Уровни, снизу вверх, с честным ответом «работает/не работает»:

| Стадия | Что значит | Что НЕ доказывает |
|---|---|---|
| `parse` | ссылка разобрана Go-парсером | ничего не проверяет, но отделяет «кривую ссылку» от «мёртвого сервера» |
| `start` | поднялся sing-box inbound/outbound для этого профиля (порт, DNS-резолв хоста) | сервер жив |
| `dial` | SOCKS5 CONNECT через этот outbound дошёл до сервера (VLESS/hy2/trojan handshake, auth) | данные идут |
| `payload` | **через туннель** прошёл TLS-handshake до внешней цели (байты в обе стороны) | скорость |

**Проверяем именно end-to-end (`payload`)**, а не TCP-connect и не отдельный TLS-handshake к SNI. Причины:
- TCP-connect к `host:port` показывает только доступность порта: сервер принимает соединение и на мёртвом конфиге (переименованный UUID, сменённый `pbk`) — это ровно тот случай, из-за которого владелец и просит кнопку;
- TLS-handshake к `sni` для Reality проходит против любого живого хоста-прикрышки независимо от `pbk`, т.е. врёт;
- `payload` ловит обе беды сразу: «не пускает» и «пускает, но не везёт» (тот самый `unknown version: 72` из лога, `relay_dial_live_test.go:28`).

Цель проверки: `www.gstatic.com:443`, TLS-handshake, `InsecureSkipVerify: true` (сертификат цели не наш предмет — нам нужен факт прохождения байтов). Константа в Go, не в UI.

### 5.2 Переиспользование, а не новый клиент

Тест **не** пишет собственный dialer. Уже есть всё нужное:

- `internal/transport/android/relay.go:112 func (r *Relay) Start(ctx, protect, filesDir) error` — поднимает sing-box для набора эндпоинтов;
- `relay.go:270 func (r *Relay) DialTCPIndex(idx, ctx, dst)` — CONNECT через конкретный carrier (SOCKS5 к loopback-inbound);
- `settings.go:94 ParseSettings` — собрать `Settings` с одной ссылкой: `{"fallback":true,"links":["<link>"]}`.

Т.е. тест одного профиля = мини-relay на один эндпоинт + один CONNECT + TLS. Кода — десятки строк, ноль новых сетевых путей.

**`internal/prober` не переиспользуем.** `prober.Classifier` (`classifier.go:227 ProbeIP`, `:279 ProbeSNI`) классифицирует цензуру ISP и опирается на `ProbeBindIP()` (`bind.go:38`), который привязывает пробы к физическому NIC — на Android это бессмысленно (нет «физического адаптера» в этом смысле) и, главное, он не проверяет креды профиля. Другая задача, другой ответ.

### 5.3 Go API

```go
// mobile/core.go
// TestProfile поднимает транспорт ровно для одной ссылки и проверяет,
// что через неё проходят байты. Не трогает settings/engine (можно звать
// при работающем VPN). filesDir — Context.getFilesDir(): нужен для
// кэш-файла временного sing-box.
func TestProfile(link, filesDir string) string
```

Результат (JSON, ключи фиксированы — Java читает их как есть):

```json
{"ok":true,"ms":412,"stage":"payload","err":""}
{"ok":false,"ms":0,"stage":"dial","err":"android: relay: tunnel unavailable"}
{"ok":false,"ms":0,"stage":"payload","err":"tls handshake: i/o timeout"}
{"ok":false,"ms":0,"stage":"busy","err":"уже идёт проверка другого профиля"}
```

- `ms` — полное время до завершения TLS-handshake; при `ok:false` = 0 (время отказа не показываем: у таймаута оно всегда равно таймауту и не информативно).
- `err` — текст ошибки ядра, **обрезанный до 200 символов** и без секретов (§9.1). Java показывает его в раскрытой карточке, не в основном статусе.
- Форма не конфликтует с `TestRoute` (`mobile/core.go:265`): другое имя, другой JSON (`TestRoute` отдаёт `{error}` / `{stage,stageName,matcher,action,note}`), другой смысл (правила vs сеть), разные глобалы (`ruleSet` vs `probeMu`). `gobind` даст `core.Core.TestProfile(String,String)` рядом с `core.Core.TestRoute(String)`.

### 5.4 Хуки ядра, которые нужны

**Ни одного нового.** Обоснование по каждому:

- **protect-сокет** — не нужен: пакет приложения исключён из VPN (`RupasVpnService` → `b.addDisallowedApplication(getPackageName())`), поэтому его исходящие сокеты и так идут мимо TUN. `Relay.Start` принимает `protect ProtectFunc` — передаём `nil` (комментарий `relay.go:110` разрешает nil на не-Android).
- **dial через туннель** — уже есть `DialTCPIndex`.
- **sing-box outbound** — уже собирается внутри `Relay.Start` из `Settings.Endpoints()`.
- **Своя рабочая директория** — единственное, что добавляется: `filepath.Join(filesDir, "probe")`, `os.MkdirAll`. Причина: `Relay.Start` кладёт кэш sing-box по фиксированному пути в `filesDir`; второй экземпляр box на том же файле конфликтует с боевым relay. Отдельный подкаталог убирает конфликт и заодно не требует `Start()` (то есть `filesDir` больше не зависит от поднятого VPN — параметр передаёт Java).

### 5.5 Таймауты и параллельность

- Общий контекст: **8 с** (`context.WithTimeout`), внутри — свои дедлайны стадий. Внешний и жёсткий, потому что `android.DialTimeout = 15 s` (`egress.go:15`) для UI слишком долго.
- Разбивка бюджета: `start` ≤ 3 с, `dial` ≤ 3 с, `payload` ≤ 2 с. Стадия, в которой кончилось время, и есть `stage` отказа.
- **Один тест за раз.** `sync.Mutex.TryLock()` (Go 1.26, есть в `go.mod`) — второй вызов сразу получает `stage:"busy"`, а не встаёт в очередь: пользователь видит отказ мгновенно, никакой очереди из N профилей по 8 с.
- Сериализация обязательна: каждый тест поднимает свой sing-box (~100–300 мс + свободный порт), параллельный запуск нескольких box'ов на телефоне — лишний расход и лишние точки отказа.
- UI: на время теста кнопки «Проверить» остальных карточек disabled (визуально `ink_faint`), чтобы `busy` не выглядел как баг.

### 5.6 Как результат живёт в UI

- Состояние теста — **в памяти Activity**, не в prefs: `Map<String id, Result>`. Перезапуск приложения = «не проверялся». Проверка — снимок, а не свойство профиля; сохранять её в prefs значило бы показывать вчерашний «работает» на мёртвом сервере.
- Поток: `Executors.newSingleThreadExecutor()` (один поток на процесс, поля не нужны), результат → `runOnUiThread` → обновление одной карточки по `id`.
- Карточка, удалённая во время теста: результат приходит по `id`, которого уже нет в списке → молча игнорируется (проверка существования перед обновлением).
- Отмена: при `onDestroy` executor `shutdownNow()`; Go-вызов не прерывается (контекст внутри), но его результат некуда писать — безопасно, `String` уже вернулся. Отдельный `cancel` в этот этап не берём (лишний API ради 8 с).
- Прежний результат сбрасывается при правке ссылки у профиля (старый «работает» относится к другому конфигу).

## 9. Риски

### 9.1 Секреты в логах — высокая цена ошибки
`link` содержит `uuid`/пароль (vless/trojan/hysteria2). Правила:
- в `LogBuffer.add()` и `Toast` — **только** `label`, `stage`, `err` без userinfo;
- `err` из ядра прогонять через обрезку + вычищать `link`-подстроку (sing-box умеет эхоить конфиг в ошибке);
- в JSON-результате `link` отсутствует по определению (§5.3);
- `LogBuffer.dump()` уходит в «Поделиться» (`MainActivity`, экспорт журнала) — значит любая утечка уезжает из устройства.

### 9.2 Потеря профилей при миграции — высокая цена ошибки
- миграция пишет `profiles` **до** любого использования, одним `edit()`;
- `K_LINKS` не очищается никогда (§7);
- миграция не бросает исключений: битая ссылка всё равно становится профилем (пользователь удалит её вручную), а не исчезает;
- при исключении в `load()` — ловим, показываем `settings_load_failed`, `links` цел, следующий запуск повторяет миграцию.

### 9.3 Тест через поднятый туннель vs без него
- Пакет исключён из VPN → тест всегда идёт **напрямую**, мимо TUN. Это значит: «профиль работает» относится к чистому каналу, а не к ситуации «мой трафик сейчас в TUN с DNS-фильтром/adblock». Возможен случай «тест зелёный, а трафик не идёт» (например, пер-приложение правила или adblock ломают поток).
- Поэтому в подписи блока — «Проверка идёт напрямую, не через VPN» (`profile_test_hint`), а живой статус (`carriers.active/cooldown`, §6.5) показывается отдельно. Владелец видит обе правды.
- Тест при поднятом VPN параллельно с боевым relay: два sing-box, два набора портов, разные кэш-файлы (§5.4). Проверить на устройстве в первую очередь.

### 9.4 Батарея
- Автотеста по расписанию **нет** и в этот этап не берём: 8 с sing-box + TLS на каждый профиль при пробуждении телефона — это десятки секунд радио на ровном месте.
- Тест только по явному тапу; сериализован (один box за раз); `shutdownNow()` на `onDestroy`.
- Если владелец захочет авто-проверку при старте VPN — отдельным решением с бюджетом (например, проверить только primary, 8 с, один раз за сессию).

### 9.5 Прочее
- **`DisallowUnknownFields`** (`settings.go:94`): любые новые ключи в JSON ломают старт. Профили новых ключей не вводят — держать этот инвариант при ревью.
- **`busy` как отказ**: при быстром тапе по трём карточкам две получат «идёт проверка другого профиля». Это ожидаемо, но текст должен читаться как «подождите», а не как «сломано».
- **XHTTP-профиль**: `NeedsXHTTP()` (`sharelink.go:63`) выносит эндпоинт из sing-box — `Relay.DialTCPIndex` вернёт «not a sing-box carrier». Тест такого профиля в этом этапе **не поддерживается**: честный ответ `stage:"start"` с текстом «XHTTP-профиль не проверяется этой сборкой». Иначе владелец увидит ложное «не работает» на рабочем профиле.

## 10. Вопросы владельцу — ОТВЕТЫ (2026-10-28)

1. **Статус «в работе» на карточке** → **показывать любую полезную информацию**: метка (из `#fragment`, иначе `host:port`), тип, `host:port`, SNI, вкл/выкл, результат теста. Статус `active`/`cooldown` из `Status.carriers` — можно, если не превращает строку в кашу.
2. **Ноль включённых профилей** → **разрешён**. Но предупреждение обязано быть явным и заметным: в блоке профилей И на главном экране («Нет активных профилей — VPN не подключится»).
3. **`SettingsActivity.java` + `activity_settings.xml`** → мёртвый экран, в этой ветке не трогаем (удаление — отдельным коммитом после мержа).
4. **Цель теста** → **любой заблокированный сайт**, конкретно `medium.com:443` (в коде: `104.16.124.96:443`, TLS SNI `medium.com`). Google-адрес не используем: нужен именно признак «прошло через туннель к заблокированному ресурсу».
5. **Ручной ввод без share-ссылки** → оставляем как раскрывающийся блок «Поля сервера»: его всё ещё пишет `MainActivity.saveSettingsForm()`, ломать не нужно.
6. **Автопроверка при включении VPN** → **нет**, только по кнопке (батарея).
7. **XHTTP-профили** → «не проверяется этой сборкой» приемлемо, `stage` вернёт ошибку с явным текстом.
8. **Порядок мержа** → 0.4.x в master → rebase worktree → мерж; AAR пересобирается после мержа Go-части.
