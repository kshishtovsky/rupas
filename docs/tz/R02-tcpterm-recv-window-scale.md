# R02 — терминатор rupas: окно приёма 64 КиБ запирает upload

**Severity:** High (симметричный потолок: upload упирается в те же `окно / RTT`)
**Репозиторий:** `E:/rupas`
**Слой:** userspace TCP-терминатор (`internal/tunnel/tcpterm.go`)

## Зачем

Скачивание уже вылечено: в SYN-ACK появилась опция WS
(`tcpterm.go:1406-1446`, коммиты `616c396`, `6e79bee`), поэтому клиент
масштабирует **своё** окно, и в полёте может быть больше 64 КиБ.

Обратное направление по-прежнему заперто: **наше** окно приёма —
`recvBufCap = 0xFFFF` (64 КиБ, `tcpterm.go:405`), а в SYN-ACK мы объявляем
сдвиг 0 (`tcp[27] = 0`, `tcpterm.go:1436-1438`). Мы физически не можем
объявить клиенту больше 65 535 байт несмасштабированного окна, значит upload
одного потока = `65535 / RTT`:

```
25 мс → 20.97 Мбит/с      30 мс → 17.5 Мбит/с      71 мс → 7.4 Мбит/с
```

Тот же потолок, что был у download, только с другой стороны.

## Что менять

Файл: `internal/tunnel/tcpterm.go`.

1. Константы (около `:386-409`):

```go
const (
	// recvWSShift — сдвиг окна, который МЫ объявляем в SYN-ACK (RFC 7323).
	// Он масштабирует наше приёмное окно, а не клиентское.
	recvWSShift = 5                       // ×32
	recvBufCap  = 512 << 10               // 512 КиБ приёмного буфера на поток
	termWindow  = recvBufCap >> recvWSShift // 0x4000: стартовое окно в полях
)
```
   Обоснование размера: `512 КиБ / 30 мс = 136 Мбит/с` на поток при 512 КиБ
   памяти на активный upload-поток (худший случай — все потоки залиты).

2. `recvWindowLocked()` (`:1049-1066`): считать свободное место в байтах как
   сейчас, но **возвращать поле**: `uint16(free >> c.wsShift)`, с ограничением
   `0xFFFF`. Слотовая граница (`cap(c.writeCh) - len - oooBatchReserve`) тоже
   переводится в поля после пересчёта в байты.

3. Сдвиг хранится на соединении: `wsShift uint8` в `termConn`, значение
   выбирается при обработке SYN:

```go
// Клиент, не предложивший WS, масштабирование не поймёт (RFC 7323 §2.2):
// такому потоку остаётся несмасштабированное окно 64 КиБ.
if syn.hasWS { c.wsShift = recvWSShift }
```
   Парсер SYN должен отдавать признак наличия опции WS, а не только значение
   (`tcpterm.go:170-172`: `WScale uint8` → добавить `hasWS bool`; нулевой сдвиг
   при наличии опции — легальное значение, различать обязательно).

4. `craft()` (`:1436-1440`): объявлять `tcp[27] = c.wsShift` вместо жёсткого 0
   на SYN-ACK; в остальных сегментах окно уже приходит из
   `recvWindowLocked()` и потому масштабировано.

5. `windowUpdateStep` (`:1073`): порог сравнения `advWin` теперь в **полях** —
   `(recvBufCap / 4) >> recvWSShift`. Иначе шаг будет в 32 раза больше
   реального и window-update перестанет приходить вовремя (client встанет на
   persist-таймере).

6. Обновить комментарии `:391-409` и `:1436-1440`: они прямо утверждают
   «we advertise shift 0, our receive buffer is 64 KiB» — после правки это
   неверно.

## Критерии приёмки

1. `TestSynAckCarriesWindowScale` — обновить: при SYN с WS ожидается
   `tcp[27] == recvWSShift`, при SYN без WS — `tcp[27] == 0`.
2. `TestRecvWindowScaled` (новый): после 512 КиБ в очереди объявленное поле
   равно `free >> 5`, а не `free`; при `free == 0` — ровно 0 (persist-логика
   жива), при `free == 512 КиБ` — `0x4000`.
3. `TestTerminatorUploadThroughput` (новый, по образцу
   `tcpterm_throughput_test.go`): ACK раз в 30 мс, клиент заливает данные;
   принято ≥ **4×** от прежних 64 КиБ за окно (то есть ≥ 256 КиБ), и ноль
   eviction/`ooo` в счётчиках. Тест должен падать на старом коде.
4. `TestNoWSClientStaysUnscaled`: клиент без WS в SYN → окно ≤ 0xFFFF и upload
   не превышает 64 КиБ за RTT (обратная совместимость).
5. Зелёные: `TestTerminatorAdvertisesRealWindow`, `TestTerminatorZeroWindowUpdate`,
   `TestTerminatorWindowScaleThroughput`, `TestTerminatorSlowCarrierZeroLoss`.
6. `go test -tags "with_utls with_quic" -count=1 ./internal/tunnel/` и
   `go test -tags "with_utls with_quic" -count=1 -short ./...` — зелёные.
7. `mingw32-make build` собирается.

## Риск

Высокий: это ядро потока данных TCP-терминатора. Главная опасность —
рассинхрон «объявили больше, чем помещается в буфер» (клиент зальёт 512 КиБ,
мы уроним в eviction). Поэтому: объявленное поле всегда считается из
**фактически свободного места**, а не из константы, и слотовая граница
остаётся вторым ограничителем.
