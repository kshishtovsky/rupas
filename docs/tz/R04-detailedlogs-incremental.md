# R04 — `DetailedLogs`: чтение всего файла на каждый опрос

**Severity:** Medium (GC-давление и джанк в панели «Подробно»)
**Репозиторий:** `E:/rupas`
**Слой:** `internal/guictrl/service.go`
**Исполнитель:** оркестратор (сам), после завершения R03 (чтобы не пересечься
по файлам с подагентом GUI)

## Зачем

`Controller.DetailedLogs` (`internal/guictrl/service.go:98-130`) на каждый вызов:

1. открывает файл лога демона,
2. читает **последние 512 КиБ** целиком (`io.ReadAll`),
3. `strings.Split` на строки (ротейд 10 МиБ → ~10 000 строк),
4. отдаёт хвост из `limit` строк.

Панель «Подробно» опрашивает метод каждые 2 с (`app.js:148,157`), то есть
каждые 2 с в процессе GUI создаётся ~512 КиБ мусора и ~10 000 строк — это
видимый джанк прокрутки панели и лишняя работа GC. Сам код это признаёт:
`// shortcut: reads the whole file up to tailBytes on every call, fine for a
10 MiB rotated log; switch to a tracked offset if the poll gets hot.`

Опрос стал горячим: владелец держит «Подробно» открытым именно тогда, когда
что-то не работает.

## Что менять

Файл: `internal/guictrl/service.go`, метод `DetailedLogs`.

Инкрементальный кэш хвоста в `Controller`:

```go
type logTail struct {
	mu    sync.Mutex
	path  string
	off   int64      // прочитано до этой позиции
	lines []string   // накопленный хвост (не длиннее maxTailLines)
}
```

Алгоритм:
1. `Stat` файла. Если `Size() < off` (файл ротирован/усечён) или размер не
   изменился — отдать текущий хвост из кэша, к диску не ходить.
2. Иначе прочитать только `[off, Size())`, разбить по `\n`, добавить в
   `lines`, обрезать хвост до `maxTailLines` (10 000 — при среднем 60 байт
   это ~600 КиБ в памяти, тот же порядок, что и раньше).
3. `limit > 0` — вернуть последние `limit` строк (как сейчас).
4. Кэш инвалидируется сменой пути (демон мог перезапуститься с другим `-log`).

Кэш живёт в `Controller`, а не в пакете: у GUI один контроллер, а пакетные
переменные уже один раз приводили к утечке состояния между тестами.

## Границы

Трогать можно: `internal/guictrl/service.go`, `internal/guictrl/update_test.go`
не трогать; новый тест — `internal/guictrl/detailedlogs_test.go`.

## Критерии приёмки

1. `TestDetailedLogsIncremental`: файл 300 КиБ → первый вызов читает всё;
   дописать 10 строк → второй вызов отдаёт те же первые строки + новые, и
   **не** перечитывает файл (проверить счётчиком чтений через подменяемый
   `*os.File`-хук или по размеру аллокаций в `testing.AllocsPerRun` — сигнатура
   и результат важнее способа).
2. `TestDetailedLogsTruncated`: файл усечён (симуляция ротации) → кэш
   сбрасывается, читается заново, старые строки не смешиваются с новыми.
3. `TestDetailedLogsLimit`: `limit = 1500` при 5000 строк в файле → ровно 1500
   последних.
4. `go test ./internal/guictrl/ -count=1` зелёные (существующие
   `detailedlogs_windows_test.go` должны пройти без правок).

## Риск

Низкий. Единственная тонкость — ротация: при `Size() < off` кэш обязан
сброситься, иначе панель покажет смесь двух поколений файла.
